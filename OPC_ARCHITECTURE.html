02三轨治理：风险决定自动化程度

第 ④ 步服务端按任务风险（关键词 + 风险打分）把每个任务分到一条轨道，决定它能不能自动跑。

🟢 绿轨 · 自动执行

只读 / 分析类低风险任务。直接在受治理沙箱里自动跑完，无需确认。读文件、查资料、总结。

🟡 黄轨 · 需确认

会改动工作区的任务（写文件、执行 shell）。必须有人工确认回执才执行。完全权限下前端自动代为确认。

🔴 红轨 · 高风险

生产/删数据/支付类。需显式人工批准 + 紧急租约 + 真 Ed25519 双签（监控签 + 诊断签）才放行。

关键安全修复（本轮）：绿轨任务映射到只读沙箱，此前却能调用 workspace-write-file/workspace-shell 写盘——已修：非黄轨一律禁用写/执行类工具。

03AgentSubHarness 内部：ReAct 治理循环

这是单个 AI 员工"干活"的真实循环（最多约 16 轮）。每一次工具调用都必须穿过治理门 GovernGate，没有旁路。

⟳ ReAct Loop（crates/coevo-worker/src/agent_harness.rs · loop/govern.rs）
1
BuildContext 构建上下文
装载公司记忆、技能、员工护照、任务合约。
2
ModelCall 调真实大模型
OpenAI / DeepSeek / Anthropic 真 HTTP+SSE 流式。模型返回"思考 + 提议的动作"。
3
GovernGate.adjudicate 治理裁定 闸门
对提议的动作裁定：允许 / 拒绝 / 需审批。先过 ToolPolicy（工具粗筛），再过 RiskGate（策略引擎 → 一票否决 → 信心 vs 风险）。
4
执行工具 / 外部执行器
本地 5 工具（读文件/HTTP/写文件/shell/GitHub）或绑定的外部执行器（Docker/本地进程/HTTP 运行时）。只读轨在 OS 沙箱守卫内（Windows icacls / Unix chmod）。
5
Observation 观察结果
工具结果写回历史，作为下一轮的输入。
6
判定：继续循环 or finish
没完成就回到第 2 步；完成则产出结果 + 反思（Reflection）+ 可能的技能进化提议。
治理不变量（写死在架构里）：① 轨道由服务端权威判定，客户端不可信；② 一切工具调用必经 GovernGate 且落 worker_events；③ 模型输出永远不等于授权；④ 事实写入必须有来源证明（认知海关）。

04AI 员工之间怎么"通信"？（三层智能协作）

已从"写死的脚本编排"升级为三层智能组织：秘书智能调度 → 部门主管 → 主管按 skill 动态建子团队，主管之间通过真实 A2A 总线通信。

秘书智能调度 真实
建公司自动创建的秘书 agent，用真大模型理解创始人意图，产出"分派计划"（understanding + 该派哪些部门）。关键词分类降级为兜底。
handlers/dispatch.rs · seed.rs SECRETARY_AGENT_ID
主管动态建 subagent 真实
ReAct 循环新增 spawn_subagent 提议：主管按 skill 临时召集子助手。治理守卫：只能委派主管自己持有的 skill，不可递归。
loop/proposal.rs · agent_harness.rs SpawnSubagent 臂
主管间 A2A 通信 真实
真·进程内消息总线：注册表 + 真实投递到收件箱（不再是 echo）。会议室/辩论的立场由角色自然产生（风控/治理类天然质疑），非写死 critic 必反对。
coevo-adapters/a2a_router.rs InProcessA2aRouter · organization.rs inferred_stance
三种通信，各归其位： 调度（秘书→主管，dispatch.rs LLM 规划）· A2A（主管↔主管，InProcessA2aRouter 真投递）· subagent（主管→子助手，spawn_subagent 受治理）。 治理不变量仍在：秘书/主管/subagent 只"提议"，轨道与授权永远由服务端治理判定。 跨系统/跨公司的标准 A2A（Google 协议）是未来在此进程内总线之上加传输层的扩展点。
